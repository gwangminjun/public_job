# 일기장 추가 디자인과 기능 설계

작성일: 2026-09-14. 추가 기능은 구현 전 제안이며, 우선 방향은 기록·회고 중심이다.

## 이번 디자인 반영

- 목록·캘린더·글쓰기에 페이지 제목과 안내 문구를 추가한다.
- 목록 날짜에 연도를 표시해 지난 기록과 구분하고, 작성자를 작은 배지로 표시한다.
- 빈 목록에 첫 일기 작성 버튼, 상세에 목록 복귀 링크와 빈 댓글 안내를 둔다.
- 작성 화면에 날짜·기분·본문·사진의 보이는 라벨을 제공한다.
- 기존 차콜·로즈 색상과 모바일 버튼·입력창 크기를 유지한다.

## 1차: 기록을 찾고 고치기

### 일기 수정

상세 화면의 작성자에게 수정 버튼을 제공한다. `/diary/[id]/edit`에서 기존 날짜·기분·본문을 불러오고, 저장 후 상세로 이동한다. 1차 수정에서 사진은 그대로 보존하며 사진 교체는 2차에서 제공한다.

기존 `PUT /api/diary/entries/[id]`를 활용한다. 현재 수정·삭제 API는 인증 여부만 검사하므로 본인 일기만 수정·삭제하도록 서버에서 작성자 조건을 적용한다. 이 권한 정책은 제안 기본값이다. `/api/diary/me`는 현재 작성자 ID와 표시 이름만 반환하고 비밀번호는 응답에 포함하지 않는다. 댓글 삭제도 같은 작성자 정책으로 맞춘다.

저장 중 버튼 중복 실행을 막고 실패 시 입력을 보존한다. 날짜·기분·본문 형식을 서버에서 검사하고 잘못된 JSON은 400으로 응답한다. `updatedAt`을 수정 요청에 포함해 오래된 화면에서 저장하면 409로 충돌을 알린다. 성공하면 목록·상세·캘린더 쿼리를 갱신한다.

### 검색·필터

목록 제목 아래에 본문 검색창을, 그 아래에 월·작성자·기분 필터를 둔다. 모바일에서는 필터를 접을 수 있게 하고 적용 개수를 표시한다. 초기화 버튼과 검색 결과 없음 상태를 제공한다.

`GET /api/diary/entries?q=&month=&author=&mood=&cursor=&limit=`로 서버에서 필터링한다. 검색은 본문 부분 일치, 필터는 AND 조건이다. 월은 일기 날짜 기준이며 날짜 → 생성 시각 → ID 역순으로 정렬한다. 필터 변경 시 커서를 초기화하고 URL 검색 매개변수에 상태를 보존한다. React Query 키에 모든 조건을 포함한다.

응답은 `{ entries, nextCursor }`로 확장한다. 목록의 첫 요청은 20개, 최대 50개로 제한한다. 본문은 요약만, 사진은 카드에 필요한 최대 3개만 반환하고 전체 사진은 상세에서 조회한다. 사진 서명 URL도 요청에 필요한 항목만 생성한다.

### 날짜별 여러 일기

현재 캘린더의 `Map<string, DiaryEntry>`는 같은 날짜의 여러 일기를 한 건으로 덮어쓴다. 날짜별 배열을 사용해 선택 날짜 아래에 작성자·기분·본문 미리보기 목록을 표시하고, 작성된 날에도 새 일기 쓰기 버튼을 제공한다.

`GET /api/diary/calendar?month=YYYY-MM`은 화면에 보이는 앞뒤 달 날짜까지 최대 42일을 조회한다. 응답은 날짜별 `{ date, count, entries: [{ id, author, authorName, mood, excerpt }] }` 형태로 제공한다. 월별 요약에는 해당 월의 일기 건수와 서로 다른 작성일 수만 포함한다. 사진 URL은 생성하지 않는다.

## 2차: 편하게 남기고 돌아보기

| 기능 | 화면과 동작 | 저장 방식 |
| --- | --- | --- |
| 사진 미리보기 | 저장 전 썸네일, 개별 제거, 개수·용량 안내 | 선택 파일 배열과 object URL, 교체·언마운트 시 해제 |
| 임시 저장 | 작성 화면에 저장 시각과 복원·버리기 제공 | 서버 임시 저장 테이블, 작성자별 분리, 날짜·기분·본문 저장 |
| 월별 회고 | 캘린더 상단에 기록 수·작성일 수·기분 분포 | 월별 집계 API, 데이터가 없으면 0과 안내 문구 |

사진 제한 제안은 최대 6장, 장당 10MB, JPEG·PNG·WebP다. 클라이언트와 서버 양쪽에서 검증하고 업로드 실패 시 기존 파일 선택을 유지한다. 부분 업로드와 DB 실패 시 생성한 파일을 정리한다.

임시 저장은 입력 종료 2초 뒤 동작하며 사진은 1차 임시 저장 범위에서 제외한다. 저장 상태를 화면에 표시하고, 실패하면 입력을 유지한다. 작성 완료가 확인된 뒤에만 초안을 삭제한다. 여러 탭 충돌에는 수정 버전을 사용한다. 비밀 일기 본문을 공용 기기의 localStorage에 자동 보관하지 않는다.

## 데이터 변경

1차는 기존 일기·댓글 테이블을 사용한다. 목록 조회용 `(entry_date DESC, created_at DESC, id DESC)`와 댓글 조회용 `(entry_id, created_at)` 인덱스를 새 마이그레이션에 추가한다. 본문 검색 인덱스는 실제 데이터량과 실행 계획을 보고 판단한다.

2차 임시 저장용 `diary_drafts`는 `author` 기본 키, `entry_date`, `mood`, `content`, `version`, `updated_at`으로 구성한다. 기존 테이블처럼 RLS를 켜고 서비스 역할 API에서만 접근하며, API가 요청 작성자 범위를 강제한다. 여러 초안은 초기 범위에 포함하지 않는다.

## 구현 순서와 완료 기준

1. 작성자 식별·수정 화면·권한 검사·실패 상태를 구현한다. 타인 수정 및 삭제 차단, 입력 보존, 충돌 감지, 저장 후 화면 갱신을 확인한다.
2. 캘린더를 날짜별 다건 조회로 전환한다. 같은 날 A/B의 기록, 여러 기록, 빈 날짜, 앞뒤 달 날짜, 월 이동을 확인한다.
3. 검색·필터와 페이지 나누기를 구현한다. 복합 필터, 검색 초기화, 뒤로 가기, 동일 날짜 경계에서 중복·누락 없는 다음 페이지를 확인한다.
4. 사진 미리보기 → 서버 임시 저장 → 월별 회고 순서로 확장한다.

각 단계에서 lint·TypeScript·production build를 실행하고 320/375/768px 폭 및 데스크톱의 밝은·어두운 테마에서 확인한다. 키보드 포커스, 긴 이름과 본문, 오류·빈 화면, 모바일 가로 넘침을 검증한다. 인증·권한·커서 경계처럼 실제 실패 가능성이 있는 동작에 테스트를 추가한다.

현재 환경은 `SUPABASE_URL`이 없어 전체 빌드의 `/bookmarks` 사전 렌더링이 중단된다. 실제 API 통합 검증에는 설정된 Supabase 환경이 필요하다. 기존 `perf:audit`는 루트 페이지를 측정하므로 일기장 성능은 인증된 일기장 화면을 별도로 측정한다.
